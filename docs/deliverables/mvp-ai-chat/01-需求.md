# 需求：mvp-ai-chat

> 交付物 01 · 由 /flow-grill 产出 · 设计/开发阶段以本文档为输入

## 背景与动机

咕噜（gululoop）项目的第一阶段目标：打通"用户发消息 → 后端调用 LLM → 流式输出 → 会话管理"这条核心链路，提供一个可实际使用的 AI 聊天 MVP。

不做这件事的代价：用户无法和 LLM 进行对话，后续 Agent、知识库等能力无从谈起。

## 目标

1. 用户能在 Web 界面发起多轮对话，服务端流式返回 LLM 响应。
2. 服务支持多服务商配置：用户**激活**其中一个服务商，聊天页的模型切换只在**该服务商**的模型清单内进行（激活是全局唯一的，所有会话共享）。
3. 会话历史持久化，上下文过长时自动摘要压缩。
4. 用户可对消息执行重试、编辑后重发、复制内容等操作。
5. 会话列表、重命名、删除、导出 Markdown 可用。

## 非目标

- 用户认证 / 多租户（MVP 单用户）
- Agent / 工具调用 / ReAct 循环（第二阶段）——但本阶段的选型（LLM 客户端、消息模型）**必须为它让路**：流式响应要能透传 `tool_calls` 增量，不能把协议细节焊死在业务里（ADR-0014）
- 知识库 RAG
- 笔记 / 其他功能模块
- 服务商管理的管理员面板（仅基础 CRUD）
- **模型能力与参数元数据**：图片识别（vision）、工具调用、token 计费、弃用标记、别名、采样参数（`temperature` / `max_tokens`）、上下文窗口 —— MVP 只做聊天、不做图片识别，这些字段**不存、不显示、不校验**；键名先在 `02-后端设计.md` 预留，将来加不写迁移

## 用户与场景

- 目标用户：单用户本地运行者（个人开发者）
- 典型场景 1：在服务商页激活一个服务商 → 回到聊天页从它的模型清单里选模型 → 输入问题 → 看到流式回复。
- 典型场景 2：连续多轮对话，上下文自动摘要压缩，不影响响应质量。
- 典型场景 3：对某条回复不满意，点击"重试"重新生成；或修改自己上一条问题后重发。
- 典型场景 4：将一次有意义的对话导出为 Markdown 文件保存或分享。

## 功能需求

| # | 功能点 | 描述 | 验收标准（可检验） |
|---|--------|------|--------------------|
| 1 | 服务商配置 | 添加/编辑/删除服务商：base_url、api_key、模型清单、默认模型 | 1. POST /api/v1/service-providers 新增成功，GET 可查到；2. PUT /api/v1/service-providers/{name} 更新生效（`apiKey` 传空串 = 不修改）；3. DELETE 后列表中消失；4. 每个服务商必须配置 base_url、api_key 与**至少 1 个模型**；5. 响应**永不回传 api_key**，只给 `hasApiKey` 布尔 |
| 1b | 模型清单 | 每个服务商维护一个模型清单（模型标识 + 可选展示名），其中一个为默认模型 | 1. 模型按 `[{id, name?}]` 存储，`name` 缺省等于 `id`；2. **默认模型必须属于模型清单**，否则 400 `默认模型必须在模型清单中`；3. 模型标识在服务商内不可重复（忽略大小写），否则 400 `模型标识重复：<id>`；4. 模型清单不可为空，否则 400 `至少配置一个模型`；5. 存量字符串数组 `["a"]` 读成 `[{id:"a",name:"a"}]`，无数据迁移 |
| 1e | 服务商列表 | 服务商设置页一览全部服务商，每行含名称、icon、官网地址、编辑与更多操作 | 1. 每行展示：服务商名称、icon（首字母方块）、模型数、官网地址；2. 官网地址可点击（新标签打开），留空则不显示该行；3. 行尾有「编辑」与「⋯」两个按钮；4. 「⋯」展开下拉抽屉，含「检测连通」「删除」两项 |
| 1f | 激活的服务商 | 全局唯一地指定"当前使用哪个服务商"，决定后续所有消息调用上游时用的 base_url 与 api_key | 1. 服务商列表每行**行尾（编辑按钮之前）有一个激活图标按钮**，点即激活（**无二次确认**）；**已激活的那个按钮显示文字「激活」**（`primary-soft` 底），其余只显示图标；2. `GET /api/v1/service-providers` 每项返回 `isActive` 布尔，**恰好 0 或 1 个为 true**；3. `POST /api/v1/service-providers/{name}:activate` 激活成功并返回 204，服务商不存在返回 404；4. **表里一条服务商都没有时**（从 0 个变为 1 个）新增的服务商自动激活；5. 删除激活的服务商后进入「无激活」状态，**不自动接替**；6. **表里已有服务商但无激活**时，新增的服务商**不自动激活**，需用户手动选择；7. 激活的服务商决定 `POST …/messages` 的 base_url / api_key，`x_messages.service_provider` 记录当时的快照 |
| 1g | 检测连通 | 验证某个服务商当前配置能否正常调通上游 | 1. 从行内「⋯ → 检测连通」触发；2. 成功 toast「<名称> 连通正常，<n>ms」；3. 失败 toast 用危险样式并带原因（如「<名称> 连不上：401 api_key 无效」）；4. 检测只读，不修改配置、不落库；5. 上游超时按失败处理（60s） |
| 1h | 删除服务商（确认） | 删除前二次确认 | 1. 入口两处：行内「⋯ → 删除」、编辑页右上「删除」；2. 弹层标题「删除「<名称>」？」、正文说明模型会一起删掉、历史消息不受影响；3. 危险按钮文案「删除服务商」；4. 成功后回列表并 toast「服务商已删除」 |
| 1c | 拉取模型列表 | 从上游 OpenAI 兼容 `GET /v1/models` 拉取模型标识，供用户挑选（辅助手填） | 1. `POST /api/v1/service-providers/models:fetch` 返回 `{models:[id,...]}`；2. 新建态（未保存）用请求体里的 `baseUrl`+`apiKey` 拉取；3. 编辑态 `apiKey` 留空时用库内已存密钥（按 `serviceProvider` 取）；4. **拉取不写库**，写库仍只由保存表单那一次请求决定；5. 上游失败返回 502 并透传上游状态（如 `上游返回 401：api_key 无效`）；6. 手填路径始终可用，不依赖拉取成功 |
| 2 | 发送消息（流式） | **`POST /api/v1/messages`**（2026-10-26 从 `POST /conversations/{id}/messages` 改判）接收用户消息，调用 LLM，以 NDJSON 流式返回 | 1. 响应 Content-Type: application/x-ndjson；2. 首事件 `{"type":"meta",...}`（带 conversationId / title / userMessageId / assistantMessageId / seq / model / serviceProvider）；3. 中间若干 `{"type":"message","content":…}` 或 `{"type":"message","thinkingContent":…}`；4. 结尾 `{"type":"done","updatedAt":…,"messageCount":…}` 或 `{"type":"error","conversationId":…,"message":…}`；5. 超时 60s 返回 error 事件；6. `conversationId` 为空时后端**新建会话**（草稿态），LLM 失败时会话与 user 消息**保留**（ADR-0017） |
| 3 | 多轮对话上下文 | 每次调用 LLM 时组装：摘要 + 最近 10 条原始消息 + 当前用户问题 | 1. 消息数 ≤ 10 时，直接发送全部历史消息；2. 消息数 > 10 时，发送摘要 + 最近 10 条 + 当前问题；3. 会话切换模型后，新对话使用该模型 |
| 4 | 自动摘要压缩 | 消息数达到 10 条时，调用 LLM 生成摘要存入 x_conversation_summaries | 1. 第 10 条 assistant 消息写入后触发摘要生成；2. 摘要以最新 assistant 消息为 MessageID 关联；3. 摘要覆盖更新（upsert） |
| 5b | 新建会话（草稿态） | 新建是**纯前端行为**：不请求后端，首次发送消息时才创建会话 | 1. 点「新的聊天」**不发起任何请求**，右侧切到默认对话页（草稿态）；2. 草稿态**不出现在会话列表**里；3. 草稿态下重复点「新的聊天」**不新增会话**，只清空右侧输入框（幂等）；4. 首次发送时先 `POST /api/v1/conversations` 再发消息，成功后会话进入列表并被选中；5. 会话标题取首条用户消息内容前 20 个字符（#10）；6. 首次发送失败时会话仍存在（0 条消息、空标题），用户可手动删除；7. 无任何会话时启动，右侧即为草稿态 |
| 5 | 会话管理 | 列表、重命名、删除（级联消息和摘要）、导出 Markdown | 1. GET /api/v1/conversations 分页返回；2. PATCH /api/v1/conversations/{id} 修改标题；3. DELETE 级联删除，x_messages 和 x_conversation_summaries 均清除；4. 导出返回 Markdown 文本 |
| 6 | 消息操作：重试 | 重新调用 LLM 生成同一条 assistant 消息 | 1. 请求体携带 messageId；2. 删除原 assistant 消息及后续消息；3. 以原用户消息为输入重新发起流式调用 |
| 7 | 消息操作：编辑后重发 | 用户修改自己消息内容后重新发起 | 1. 请求体携带 messageId 和新内容；2. 删除该消息及后续所有消息；3. 以新内容重新发起流式调用 |
| 8 | 消息操作：复制内容 | 获取单条消息的纯文本内容 | 1. GET /api/v1/conversations/{id}/messages/{messageId} 返回 {content} |
| 9 | 模型切换 | 会话内切换使用的模型，**候选范围 = 激活的服务商的模型清单** | 1. `POST /api/v1/conversations/{id}/messages` 请求体可携带 `serviceProvider` + `model`，两者一起标识"用哪个服务商的哪个模型"；2. 后续消息使用该组合直到再次切换；3. 模型选择器**只列激活的服务商的模型**，不同服务商的同名模型不会同时出现；4. 激活的服务商一变，选择器立即换源；当前选中的模型不在新清单内时**回落到新服务商的默认模型**，并在消息区留下换模型痕迹；5. 未携带 `model` 时用激活服务商的默认模型；6. 无激活服务商时发送返回 400 `请先激活一个服务商` |
| 10 | 会话标题自动生成 | 根据第一条用户消息内容取前 N 字作为标题 | 1. 新建会话后第一条 user 消息写入时，自动截取前 20 字（不足则全取）设为 title；2. 用户可手动重命名覆盖 |
| 11 | 前端渲染 | Markdown 渲染 + 代码高亮（前端实现） | 1. 前端将 assistant 消息 content 以 Markdown 渲染展示；2. 代码块高亮显示 |

## 约束

- 技术栈：Go + Chi（后端），现有 SQLite + sqlx 数据层
- 流式协议：NDJSON（每行一个 JSON 对象），Content-Type: application/x-ndjson
- LLM 超时：60s（硬超时）
- 服务商格式：OpenAI Chat Completions 兼容接口（stream: true 时 SSE 响应，后端解析后转 NDJSON）
- 摘要生成：复用同一服务商/模型的 LLM，system prompt 要求生成简洁摘要
- **LLM 客户端：用官方 `openai-go` SDK，但全封装在 `internal/llm` 一个包里**（ADR-0014，取代 ADR-0013）。对外只有 `Stream` / `FetchModels` / `Summarize` 三个方法，SDK 类型不出包；**自动重试关掉**（`WithMaxRetries(0)`——流式重试会重复计费），重试语义由业务定：开流前可重试一次、写出 `meta` 之后不重试；`thinkingContent` 从 SDK 的额外字段取 `reasoning_content`，取不到就退到「中间件截获原始响应体、第二遍解析」，再不行则字段恒为空（不改表、不改前端契约）；**工具循环、上下文裁剪、摘要时机仍由业务自己写**
- 服务商存储：配置整体存于 `x_service_provider.setting_json`（JSON 文本，键名 **snake_case**），接口层用**结构化 camelCase 字段**，编解码只在 `ProviderSetting` 一处（ADR-0005）
- 模型清单存储：对象数组（`[{id, name?}]`），为将来扩展能力字段（`capabilities` / `context_window` / `pricing` 等）预留，**加字段不写数据迁移**
- 拉取模型列表：仅支持 OpenAI 兼容的 `GET /v1/models`；调用需带已配置的 `api_key`，超时与聊天调用同口径（60s）

## 边界与异常

| 场景 | 预期行为 |
|------|---------|
| 无服务商配置 | 前端提示"请先添加服务商"，禁止发送消息 |
| 有服务商但**无激活** | 服务商页与聊天页**两处**横幅提示"请先激活一个服务商"，聊天页输入区与发送按钮禁用；接口层返回 400 `请先激活一个服务商` |
| 删除正在激活的服务商 | 允许删除；删除后进入「无激活」状态，**不自动激活其他服务商**，按上一行的"无激活"处理 |
| 激活的服务商被编辑、删掉了当前选中的模型 | 同"激活变化"：选择器换源，当前模型不在新清单内则回落到该服务商的默认模型 |
| 请求携带的 `serviceProvider` 不是激活的服务商 | 400 `该服务商未激活`（不允许绕过激活直接调用任意服务商） |
| 请求携带的 `serviceProvider` 已被删除 | 400 `服务商不存在，请重新选择模型` |
| 无激活状态下点「重试」/「编辑后重发」 | 同普通发送：400 `请先激活一个服务商`（重试不豁免） |
| 服务商配置缺失必填字段 | 创建/更新时校验 base_url、api_key 非空，否则返回 400 |
| 模型清单为空 | 400 `至少配置一个模型`（不允许配出"没有模型可选"的服务商） |
| 默认模型不在模型清单中 | 400 `默认模型必须在模型清单中` |
| 模型标识重复（忽略大小写） | 400 `模型标识重复：<id>` |
| 官网链接格式非法（非 http/https） | 400 `官网链接必须是 http 或 https 地址`（留空不校验） |
| 检测连通时上游不可达 / 鉴权失败 / 超时 | 检测失败：toast 用危险样式 + 上游原因，不改任何配置 |
| 拉取模型列表时上游不可达 / 鉴权失败 | 502，message 透传上游状态；**表单已填内容与已手填的模型行全部保留**，用户可改为手填 |
| 上游不支持 `GET /v1/models` | 502 并提示"该服务商不支持拉取，请手动填写模型"；手填路径始终可用 |
| 删除服务商但历史消息引用了它 | 允许直接删（不校验引用）：历史消息的 `model` / `serviceProvider` 是字符串快照，保留原值不动，不级联、不报错 |
| LLM 调用超时（60s） | 返回 `{"type":"error","message":"调用超时"}`， assistant 消息不写入 |
| LLM 调用失败（网络/鉴权） | 返回 error 事件，assistant 消息不写入，前端展示错误提示 |
| 消息数恰好 10 条时触发摘要 | 摘要在 assistant 消息写入后异步触发，不影响当次响应 |
| 删除会话时有关联摘要 | 同一事务内先删摘要、再删消息、再删会话 |
| 重试/编辑后无后续 assistant 消息 | 正常流程，重新调用 LLM 即可 |
| 并发请求（同一会话） | MaxOpenConns=1，SQLite 串行写入，不会竞态 |

### 1.2 数据结构

```go
// Conversation —— 对应 store.Conversation，messageCount 来自 x_conversations.message_count 列（ADR-0007）
// tag 统一 camelCase（加列时曾误写为 message_count，已修为 messageCount）
type Conversation struct {
    ID              string   `json:"id"`
    Title           string   `json:"title"`
    MessageCount    int       `json:"messageCount"`      // 冗余列，写路径维护（ADR-0007）
    LastMessageTime *time.Time `json:"lastMessageTime"`  // 可空：新建会话还没有消息时为 null
    CreatedAt       time.Time `json:"createdAt"`
    UpdatedAt       time.Time `json:"updatedAt"`
}

// Message —— 沿用 store.Message，字段不变
type Message struct {
    ID, ConversationID string
    Seq                int64
    Role               string   // system | user | assistant | tool
    Content            string
    ServiceProvider    string   // assistant 才有
    Model              string   // assistant 才有
    ThinkingContent    string   // DeepSeek reasoner 用；MVP 前端不渲染，接口照常返回
    ThinkingDuration   int64    // 毫秒
    CreatedAt, UpdatedAt time.Time
}

// ServiceProvider —— 存储仍是 setting_json，**接口返回结构化字段**（ADR-0005 / ADR-0011）
type ServiceProvider struct {
    ServiceProvider string     `json:"serviceProvider"`   // 业务标识（唯一键，创建后不可改）
    Website         string     `json:"website,omitempty"` // 官网地址（仅展示 / 跳转，不参与调用；可空）
    BaseURL         string     `json:"baseUrl"`
    Model           string     `json:"model"`      // 默认模型：必须 ∈ Models（ADR-0011）
    Models          []ModelRef `json:"models"`     // 模型清单，至少 1 个
    HasAPIKey       bool       `json:"hasApiKey"`  // api_key 永不回传，只告诉前端"有没有"
    CreatedAt       time.Time  `json:"createdAt"`
    UpdatedAt       time.Time  `json:"updatedAt"`
}

// ModelRef 模型清单的一个元素（ADR-0011：对象数组，为将来加能力字段预留）
type ModelRef struct {
    ID   string `json:"id"`             // 模型标识：调上游时传给 model 字段，服务商内唯一（忽略大小写）
    Name string `json:"name,omitempty"` // 展示名；缺省 = ID（读时补齐，写时可为空）
}
```

**为什么 `models` 是对象数组而不是 `string[]`**：将来加 `capabilities`（能否看图）、`context_window`、`pricing` 时只需往元素里加键，**存量数据零迁移**；而 `string[]` 一旦有存量数据，第一次加能力字段就得写一次"字符串 → 对象"的数据迁移。能力字段 MVP 一律不做（01-需求 非目标），键名见 §2 预留表。

### 1.3 流式接口 #7 详解

**请求**

```json
{ "content": "帮我把快速排序改成 Go 泛型版", "model": "kimi-k2", "messageId": null }
```

| 字段 | 必填 | 语义 |
|------|------|------|
| `content` | 否 | 新的用户消息内容。`messageId` 为空时必填；`messageId` 指向 user 消息时必填（即"编辑后重发"） |
| `model` | 否 | 覆盖服务商默认模型；为空则用该服务商 `model` |
| `messageId` | 否 | **截断锚点**（见 ADR-0006）：<br>· 指向 **assistant** 消息 → 删除它及其后所有消息，用**它之前最近的 user 消息**作为输入（= 重试）<br>· 指向 **user** 消息 → 删除它及其后所有消息，用请求里的 `content` 作为输入（= 编辑后重发）<br>· 指向 `system`/`tool` → 400 |

**响应**：`Content-Type: application/x-ndjson; charset=utf-8`，每行一个 JSON，行间 `\n`，最后一个事件后立即关闭连接。

```json
{"type":"start","conversationId":"0192f0c4-…","userMessageId":"0192f0c5-…","assistantMessageId":"0192f0c6-…","seq":7,"model":"kimi-k2","serviceProvider":"Moonshot Kimi"}
{"type":"delta","content":"泛型版要把元素类型和"}
{"type":"delta","content":"比较函数一起参数化："}
{"type":"done","assistantMessageId":"0192f0c6-…","seq":8,"messageCount":12}
```

失败（**开流之后**）：

```json
{"type":"error","message":"调用超时"}
{"type":"error","message":"上游返回 401：api_key 无效"}
```

**关键约定（前端据此写状态机）**

1. **开流前**能判定的错误一律走 JSON 4xx，不写流：会话不存在(404)、`content` 缺失(400)、`messageId` 不存在/角色非法(400/404)、没有可用服务商(400)、同会话正在生成(409)。
2. **一旦写出 `start`，HTTP 状态就固定 200**，之后所有失败只能走 `error` 事件。
3. `assistantMessageId` 在 `start` 时就生成（UUIDv7），但**只有 `done` 才落库**；`error` 不写入（与 01-需求 一致）。
4. `delta` 只带增量 `content`，前端自己拼。
5. 60s 硬超时 → `{"type":"error","message":"调用超时"}`。
6. `done.messageCount` 是该会话写入后的消息总数，前端可直接用于侧栏计数（省一次请求）。
7. 首个 user 消息写入且会话标题为空时，后端截取 `content` 前 20 个**字符**（`[]rune`，不是字节）作为标题（01-需求 #10）。

### 1.4 导出接口 #9

**返回 JSON 而不是 `text/markdown`**：`data: {filename, content}`。理由——不破坏信封约定、中文文件名由前端用 `Blob` + `URL.createObjectURL` 触发下载（跨浏览器更稳）、错误也还能走信封。若以后要"直接下载链接"再单开一个 `text/markdown` 的路径。

`filename` 规则：`<title>.md`；`title` 为空时 `会话-<id 前 8 位>.md`；文件名中的 `/ \ : * ? " < > |` 替换为 `_`。

Markdown 格式：

```markdown
# <title>

> 导出时间：2026-10-23 10:20 · 12 条消息

## 用户

帮我把快速排序改成 Go 泛型版

## 助手（kimi-k2）

泛型版要把元素类型和比较函数一起参数化：
…
```

### 1.5 错误码约定

| 状态码 | 场景 | message 示例 |
|--------|------|--------------|
| 400 | 请求体不是 JSON / 字段非法 | `请求体格式错误`、`content 不能为空`、`title 不能为空`、`messageId 指向的消息角色不支持` |
| 400 | 业务前置条件不满足 | `没有可用的服务商，请先在服务商设置里添加`、`baseUrl 不能为空`、`apiKey 不能为空` |
| 404 | 资源不存在 | `会话不存在`、`消息不存在`、`服务商不存在` |
| 409 | 冲突 | `服务商已存在：<name>`、`该会话正在生成回复` |
| 502 | **上游失败**（仅 #14 拉取模型列表） | `上游返回 401：api_key 无效`、`上游不可达：…`、`上游超时`、`上游不支持拉取模型列表，请手动填写` |
| 500 | 内部错误（DB 等） | `内部错误，请查看服务端日志` |
| 501 | 未实现（仅开发期出现） | `接口未实现` |
| 流内 error | 上游 / 超时 | `调用超时`、`上游返回 401：api_key 无效` |

> 规则：**message 一律中文、可直出给用户**（前端直接展示，不二次翻译）。技术细节进日志不进 message。
> `PATCH /conversations/{id}` 的 `title` 会先 `TrimSpace`：**全空白视同空 → 400**，落库的是裁剪后的值（避免出现肉眼看不见的标题）。
> 删除类接口成功时**没有 `data` 字段**（`respond.go` 的 `Data` 带 `omitempty`，nil 被省略，语义等价于 `null`）：前端只判 `code === 200`，不要读 `data`。
> 删除会话是**幂等**的：重复删同一 id 第二次返回 404，前端当"已经没了"处理（本地列表照常移除）。

### 1.6 服务商接口详解（#11 / #12）

**请求体**（`POST /api/v1/service-providers`、`PUT /api/v1/service-providers/{name}` 同形）

```json
{
  "serviceProvider": "deepseek",
  "website": "https://platform.deepseek.com",
  "baseUrl": "https://api.deepseek.com/v1",
  "apiKey": "sk-…",
  "model": "deepseek-v4-pro",
  "models": [
    { "id": "deepseek-v4-flash", "name": "V4 Flash" },
    { "id": "deepseek-v4-pro", "name": "V4 Pro" }
  ]
}
```

| 字段 | 必填 | 语义 |
|------|------|------|
| `serviceProvider` | 是 | 业务标识；`PUT` 时**必须与路径参数一致**，否则 400。创建后不可改名（改名 = 删 + 建） |
| `website` | 否 | 官网地址，仅用于列表里跳转；空串 = 不显示链接。**非 http/https → 400** |
| `baseUrl` | 是 | 上游根地址（不带 `/chat/completions`） |
| `apiKey` | 创建必填；更新可空 | **空串 = 不修改**（沿用已存密钥）；创建时空串 → 400 |
| `model` | 是 | 默认模型，**必须 ∈ `models[].id`** |
| `models` | 是 | 模型清单，**至少 1 个**；元素 `{id, name?}` |

**校验规则（全部 400，逐条给可直出的 message）**

| 条件 | message |
|------|---------|
| `serviceProvider` 空 / 与路径不一致 | `serviceProvider 不能为空` / `serviceProvider 必须与路径参数一致` |
| `baseUrl` 空 | `baseUrl 不能为空` |
| `website` 非空但不是 http/https | `官网链接必须是 http 或 https 地址` |
| 创建时 `apiKey` 空 | `apiKey 不能为空` |
| `models` 缺失或空数组 | `至少配置一个模型` |
| 某元素 `id` 空 | `模型标识不能为空` |
| `id` 重复（**忽略大小写**） | `模型标识重复：deepseek-v4-pro` |
| `model` 空 | `model 不能为空` |
| `model` 不在 `models[].id` 里（同样忽略大小写比较） | `默认模型必须在模型清单中` |
| 名称已存在（仅 `POST`） | 409 `服务商已存在：deepseek` |

**校验顺序**：先字段级（空值）→ 再清单级（重复 / 默认模型归属）→ 最后落库。一次只返回**第一条**错误（不返回字段级错误数组：前端表单按 `message` 直接展示，逐条改）。

**幂等性**：`POST` 不幂等（重名 409）；`PUT` 全量覆盖、幂等；`DELETE` 幂等（重复删 404）。

### 1.7 拉取模型列表 #14 详解

**为什么是 POST 而不是 GET**：这个接口会**让服务端去调一次外部接口**并携带密钥，不是纯读——`GET` 会把 `api_key` 写进查询串（进访问日志、浏览器历史、Referer），且语义上也不是幂等读。

**请求**

```json
{ "serviceProvider": "deepseek", "baseUrl": "https://api.deepseek.com/v1", "apiKey": "" }
```

| 字段 | 必填 | 语义 |
|------|------|------|
| `serviceProvider` | 否 | 已保存的服务商标识。给了且 `apiKey` 为空 → **用库里已存的密钥**（编辑态"留空不改"的同一套语义） |
| `baseUrl` | 是 | 上游根地址；后端拼 `/models` 后请求（`{baseUrl}/models`） |
| `apiKey` | 否 | 非空 → 用请求体里的（新建态、或改了 key）；空且 `serviceProvider` 有值 → 用库里的；两者都没有 → 400 |

**响应**

```json
{ "code": 200, "message": "ok", "data": { "models": ["deepseek-v4-flash", "deepseek-v4-pro", "deepseek-chat"] } }
```

- 只返回**模型标识字符串数组**（上游 `/v1/models` 只有 id，没有展示名/能力）；顺序按上游返回，**不排序、不去重、不落库**
- 前端拿到后由用户勾选，随表单一起 `POST/PUT` 保存 —— 写库只发生在那一次请求里（01-需求 #1c）

**错误**

| 状态码 | 条件 | message |
|--------|------|---------|
| 400 | `baseUrl` 空 | `baseUrl 不能为空` |
| 400 | 既没给 `apiKey` 也没给 `serviceProvider` | `请先填写 apiKey` |
| 404 | 给了 `serviceProvider` 但库里没有这条记录 | `服务商不存在` |
| 502 | 上游非 200（鉴权 / 404 端点不存在等） | `上游返回 401：api_key 无效`、`上游不支持拉取模型列表，请手动填写` |
| 502 | 网络不可达 / DNS 失败 | `上游不可达：dial tcp …` |
| 502 | 超过 60s | `上游超时` |
| 502 | 上游返回体不是 `{"data":[{"id":…}]}` | `上游返回格式无法解析` |
| 500 | 其他（DB 读密钥失败等） | `内部错误，请查看服务端日志` |

> **上游失败统一 502、不细分 504/401**：前端只有一条处理路径（"拉取失败 → 提示 + 保留已填内容，改手填"），细分状态码只会让前端多写无用的分支。失败原因放 `message`（可直出）与日志。

### 1.8 检测连通（#15）

`POST /api/v1/service-providers/{name}/test`

```json
{ "code": 200, "message": "ok", "data": { "ok": true, "latencyMs": 312, "modelCount": 8 } }
```

- 行为：用库里的 `base_url` + `api_key` 调一次上游 `GET /v1/models`（**复用 #14 的实现**，内部是 `client.Models.List()`），200 即通；**只读，不写库、不缓存**。
- 成功 → 200 + `{ok:true, latencyMs, modelCount}`；前端 toast「<名称> 连通正常，312ms」。
- 失败 → **502** + `message` 带原因（`上游返回 401：api_key 无效` / `上游不可达：…` / `上游超时`）；前端用危险样式 toast。
- 超时 60s（同 #14）；日志记 `service_provider`、`duration_ms`、`upstream_status`，**不记 api_key**。

### 2.1 时间字段的存储与语义

SQLite 没有真正的日期类型，`DATETIME` 只是**亲和性提示**（且是 NUMERIC 亲和性，不是 TEXT）。实测（`typeof()`）：

| 写入方式 | typeof | 实际值 |
|---|---|---|
| `DEFAULT CURRENT_TIMESTAMP` | `text` | `"2026-10-23 10:26:13"` |
| 裸 `time.Time` + **默认 DSN** | `text` | `"2026-10-23 18:26:27.450842 +0800 CST m=+…"` ← 驱动用 `time.String()`：本地时区 + 微秒 + monotonic，**与 DEFAULT 不同格式** |
| 裸 `time.Time` + **本项目 DSN** | `text` | `"2026-10-23 10:26:13"` ← 与 DEFAULT 逐字节一致 |
| 传 `int64`（unix） | **`integer`** | `1792751173` |
| 数字样字符串 | **`integer`** | 被 NUMERIC 亲和性转掉 |

**规则**：格式由**驱动 DSN 参数**钉住，不封装自定义时间类型（决策见 ADR-0009）。

```go
dsn := "file:" + dbPath +
    "?_pragma=journal_mode(WAL)" +
    "&_pragma=busy_timeout(5000)" +
    "&_time_format=datetime" +   // time.Time 写成 'YYYY-MM-DD HH:MM:SS'（默认是 time.String()）
    "&_timezone=UTC"             // 读写统一 UTC，展示时前端转本地
```

- 模型字段用标准 `time.Time`；**可空字段用 `*time.Time`**（`nil` → NULL）。注意：不能用零值代替 NULL——零值会存成 `"0001-01-01 00:00:00"` 的 TEXT（实测）。
- 读侧不需要自己解析：TEXT 直接扫进 `time.Time`；NULL 扫进 `*time.Time` 得 `nil`（实测）。
- 格式统一时 TEXT 字典序 = 时间序，索引可直接用；一旦混入整数（如 unix 时间戳），**存储类变了，`ORDER BY` 会先按存储类排**（`NULL < 数字 < TEXT < BLOB`），排序错乱。若真要存整数，用驱动参数 `_time_integer_format=unix_milli` 全库一起切，不要混。

| 字段 | 语义 | 可空 |
|------|------|------|
| `created_at` | 创建时间，写入后不变 | 否 |
| `updated_at` | **只随会话元数据变更**（重命名）更新；消息写入不动它（首条消息自动生成的标题也不动它——它是消息写入的副产物） | 否 |
| `last_message_time` | **创建会话时为 NULL（不能有值）**，首条消息写入后才赋值，之后随最后一条消息刷新 | **是** |
| `x_messages.created_at` | 消息创建时间；`seq` 才是顺序真相（秒精度同一秒内无法区分） | 否 |

### 2.2 列表排序（`last_message_time` 可空带来的分叉）

`ORDER BY last_message_time DESC` 时 NULL 排**最后**（SQLite 的 NULL 最小）。实测 3 条老会话 + 2 条刚建的空会话：

| 排序写法 | 结果 | 执行计划 |
|---|---|---|
| `ORDER BY last_message_time DESC`（现状） | `[old_2 old_3 old_1 new_1 new_2]` ← **新建的空会话沉到最底** | `SCAN c USING INDEX idx_lmt` ✅ |
| `ORDER BY COALESCE(last_message_time, created_at) DESC` | `[new_2 new_1 old_2 old_3 old_1]` ← 刚建的排最前 | 无表达式索引时 `SCAN c` + `USE TEMP B-TREE FOR ORDER BY` ❌ |
| 同上 + `CREATE INDEX idx_coalesce ON x_conversations (COALESCE(last_message_time, created_at) DESC)` | 同上 | `SCAN c USING INDEX idx_coalesce` ✅ |
| `ORDER BY (last_message_time IS NULL) DESC, last_message_time DESC, created_at DESC` | 同上 | 全表扫 + 临时 B-tree ❌ |

**待定**：选 ① 现状（空会话沉底，零改动）还是 ② `COALESCE` + 表达式索引（新建即置顶）。**建议 ②**——"新建的会话看不到"比"多一个索引"代价大。

**`setting_json` 的形状**（存储格式，外部不可见；键名 **snake_case**，与接口的 camelCase 只在 `ProviderSetting` 编解码处转换）

```json
{
  "website": "https://platform.deepseek.com",
  "base_url": "https://api.deepseek.com/v1",
  "api_key": "sk-…",
  "model": "deepseek-v4-pro",
  "models": [
    { "id": "deepseek-v4-flash", "name": "V4 Flash" },
    { "id": "deepseek-v4-pro", "name": "V4 Pro" }
  ]
}
```

**读兼容（`ProviderSetting.UnmarshalJSON` 负责，唯一入口）**

| 存量形状 | 读成 |
|---|---|
| `models: ["a","b"]`（旧格式字符串数组） | `[{id:"a"},{id:"b"}]` |
| 无 `models` 字段 | `[{id: <model>}]`（沿用 ADR-0005 兜底） |
| 元素缺 `name` 或为空串 | `name = id`（补齐后返回给前端，前端不必判空） |
| 未知键（`capabilities` 等将来字段） | 忽略；`PUT` 全量覆盖时**会丢弃**——这是有意的：MVP 没有写入方，丢弃可避免脏数据累积 |

**预留键名（MVP 不存、不显示、不校验；将来加**不写数据迁移**）**

| 键 | 位置 | 含义 |
|---|---|---|
| `capabilities` | `models[]` 元素 | `["vision","tools","thinking","audio","json"]`（能否看图 / 函数调用 / 推理 / 语音 / JSON 模式） |
| `pricing` | `models[]` 元素 | `{input, output, cached_input, currency, unit}`，按每 1M tokens |
| `deprecated` / `aliases` / `default_params` | `models[]` 元素 | 弃用标记 / 别名快照名 / 默认采样参数 |
| `type` / `headers` / `proxy` / `timeout_ms` / `enabled` / `display_name` | 顶层 | 协议适配器 / 自定义头 / 代理 / 超时覆盖 / 停用开关 / 展示名 |

> 键名先在这里定死，是为了将来"加字段"时不用再改口径（前端、后端、文档三处同时对齐）；**不是**要求现在实现。

**查询约定**

- 会话列表：`SELECT * FROM x_conversations ORDER BY last_message_time DESC LIMIT ? OFFSET ?` —— 单表，走 `idx_x_conversations_last_message_time`。排序分叉见 §2.2（待定）。
- 消息列表：`WHERE conversation_id=? AND (?=0 OR seq<?) ORDER BY seq DESC LIMIT ?`，返回后 `hasMore = len(list) == limit`。
- 级联删除：单事务内 `摘要 → 消息 → 会话`（01-需求 边界表）。
- `last_message_time`：创建会话时为 NULL；每次消息写入后刷新为最后一条消息的 `created_at`；**删到没有消息时回到 NULL**（不是保留旧值）。

**服务商查询约定**

- 列表：`SELECT id, service_provider, setting_json, created_at, updated_at FROM x_service_provider ORDER BY service_provider` —— 全量、不分页（服务商数量是个位数）；`setting_json` 出库后经 `ProviderSetting` 解码，`api_key` **只在 service 内部用于调上游，绝不进响应**。
- 重名（409）：`INSERT` 前先 `SELECT 1 … WHERE service_provider = ?` 判重 → 409 `服务商已存在：<name>`；唯一索引 `uk_x_service_provider_name` 作兜底 —— 并发下撞索引（SQLite `constraint failed`）也映射成 409，**不要漏成 500**。
- 改名：**不支持**。`serviceProvider` 创建后不可改（改名 = 删除 + 新建），`PUT` 的 body `serviceProvider` 必须等于路径参数，否则 400。
- 删除：直接删行，不校验 `x_messages` 的引用（历史消息里 `service_provider` / `model` 是字符串快照，删了照样能展示历史）。
- 更新：`PUT` 全量覆盖 `setting_json`（`apiKey` 空串时先读出旧 key 再写入），单条 `UPDATE` 不开事务。

**`message_count` 维护契约（必须与消息写入同一事务，写在同一个 `dal.WithTx` 回调里）**

| 写路径 | 维护方式 |
|--------|----------|
| 新增消息（普通发送 / 重试 / 编辑后重发） | `message_count = message_count + 1`（user、assistant 各一次） |
| 截断（重试 / 编辑后重发删后续） | **重算**：`UPDATE x_conversations SET message_count = (SELECT COUNT(*) FROM x_messages WHERE conversation_id = ?) WHERE id = ?` |
| 删除单条消息 | **重算**（同上），不做 `-1` |
| 删除会话 | 行随会话消失，无需维护 |

> 原则：增量只用于"加一条"；批量删或条数不确定时一律重算。这些 UPDATE 与触发它的 INSERT/DELETE 必须在同一个 `dal.WithTx` 回调里（§3.1 规则 5）。

**删除单条消息（#8b）的派生数据契约**（同一事务内三步，顺序不可换）：

| 步骤 | SQL 要点 |
|------|----------|
| 1. 删消息 | `DELETE FROM x_messages WHERE conversation_id = ? AND id = ?` —— **双条件**，防跨会话误删；`RowsAffected = 0` → 404 `消息不存在` |
| 2. 重算会话 | `message_count = COUNT(*)`；`last_message_time = (SELECT created_at … ORDER BY seq DESC LIMIT 1)` —— 取 **seq 最大**那条而不是 `MAX(created_at)`（`created_at` 只有秒精度）；删到没有消息时自然回到 `NULL` |
| 3. 清摘要锚点 | `UPDATE x_conversation_summaries SET message_id = NULL, message_seq = NULL WHERE conversation_id = ? AND message_id = ?` —— 两个字段**同时**置空（`models.ConversationSummary` 的一致性约定），摘要正文保留（它仍然是有效上下文，只是失去锚点） |

不动 `updated_at`：那是"元数据变更"（重命名）的字段，消息增删只动 `last_message_time` 与 `message_count`（§2.1）。

**迁移策略**：列加在 `000001_init.sql`（项目未发布、无生产数据）。**已跑过 000001 的本地库不会重跑**（goose 按版本号记账）→ 删掉 `~/.gulu/gulu.db` 重建即可。若将来已上线，则改为新增 `000002_add_message_count.sql`：`ALTER TABLE x_conversations ADD COLUMN message_count INTEGER NOT NULL DEFAULT 0;` + `UPDATE … SET message_count = (SELECT COUNT(*) …)` 回填。

## 3. 模块 / 服务边界

**2026-10-23 简化（ADR-0010）**：`internal/dal/repo`（4 个 repo + `TxManager` + `Executor` 接口）已**删除**；`internal/service/service.go`（基类 `Service` + `DB`/`TxRunner` 接口）也已删除。理由：本需求只有 4 张表、13 个接口、单用户本地库，数据访问层抽象换来的"可替换/可 fake"收益为零，代价是每次改动要动 3 个文件、事务执行器要沿参数透传。**`internal/service` 包保留**，但只剩业务编排，直接持有 `*sqlx.DB`。四个包：

**四条约定**

1. **SQL 写在 service 里**（单一表的简单读写也可以直接写在 handler），执行器是 `s.db`（自动提交）或 `WithTx` 回调里的 `*sqlx.Tx`。单行查询用 `GetContext`（`SelectContext` 只吃切片），列名显式列出不用 `SELECT *`。同一段 SQL 被复用时抽成本文件内的 unexported 函数，**不新建包**。
2. **错误归一在调用方**：`errors.Is(err, sql.ErrNoRows)` → 404（`s.notFound`）；其他 → 500（`s.serverError`，日志带 `request_id`）。不再有 `repo.ErrNotFound` 这层自定义错误；service 只做 `fmt.Errorf("查询会话列表: %w", err)` 的上下文包装，不吞原始错误。
3. **事务只从 `dal.WithTx` 开**：需要原子性的写（级联删除、消息 + 计数、截断）整段包在回调里；回调内禁止 LLM/HTTP 调用。
4. **数据访问不做接口化、不引入 ORM**：没有"换存储"的需求；测试用临时目录真库 + 真迁移（`internal/dal/tx_test.go` 已验证提交/回滚/嵌套拒绝）。换 gorm/ent 的代价（重学 API、调试生成 SQL、流式场景仍要手写）大于收益。

**接缝测试**：`llm.Client` 用 `httptest` 假上游（唯一 mock）；`dal.WithTx` 与各 service 用临时真库 + 真迁移测（已验证 `ListConversations` 的分页、NULL 排序、空切片、参数兜底）；`httpapi` 用 `httptest` 测状态码与流事件序列。**不写 fake repo**（已无 repo）。

### 3.1 事务规则（决策见 ADR-0010，取代 ADR-0008）

**结构**：`dal.WithTx` 是唯一入口，回调直接给 `*sqlx.Tx`。

```go
// internal/dal/db.go
var ErrNestedTx = errors.New("已在事务中，禁止嵌套开启事务")
func InTx(ctx context.Context) bool
func WithTx(ctx context.Context, db *sqlx.DB, fn func(ctx context.Context, tx *sqlx.Tx) error) error

// internal/httpapi/conversations.go —— 事务边界就在 handler 里
func (s *Server) deleteConversation(w http.ResponseWriter, r *http.Request) {
    id := chi.URLParam(r, "id")
    err := dal.WithTx(r.Context(), s.db, func(ctx context.Context, tx *sqlx.Tx) error {
        if _, err := tx.ExecContext(ctx, `DELETE FROM x_conversation_summaries WHERE conversation_id = ?`, id); err != nil {
            return err
        }
        if _, err := tx.ExecContext(ctx, `DELETE FROM x_messages WHERE conversation_id = ?`, id); err != nil {
            return err
        }
        res, err := tx.ExecContext(ctx, `DELETE FROM x_conversations WHERE id = ?`, id)
        if err != nil {
            return err
        }
        if n, _ := res.RowsAffected(); n == 0 {
            return sql.ErrNoRows            // → handler 映射成 404
        }
        return nil
    })
    // ... 错误映射
}
```

**六条硬规则**

1. **事务只由 `dal.WithTx` 开**：handler / 别处一律不写 `BeginTxx`，否则边界散落。
2. **事务是参数不是字段**：`*sqlx.Tx` 只在回调作用域内有效，不得存进 `Server` 或任何结构体、不得跨请求复用（会拿到 `ErrTxDone`）。
3. **事务里绝不放 LLM 调用**：`MaxOpenConns=1` 下长事务会把整个服务卡住（连列表都读不了）。流式发送固定两段事务——`tx1: user 消息 + 计数` → 释放连接调上游 → `tx2: assistant 消息 + 计数`。**拉取模型列表（#14）同样在事务外**：读密钥 → 关连接 → 调上游 → 直接返回，不写库。
4. **不得嵌套 `WithTx`**：单连接下第二次 `BeginTxx` 会拿不到连接而 hang；`WithTx` 用 ctx 标记守卫，二次进入立刻返回 `ErrNestedTx`。需要组合时把操作写进同一个回调。
5. **计数维护必须同事务**（ADR-0007）：新增消息 `message_count + 1` 与 `INSERT` 同回调；批量删后用 `COUNT(*)` 重算，不做 `-N`。
6. **`Commit` 失败要与业务失败区分**：业务失败 `return err`（已回滚，确定没写入）；提交失败包 `fmt.Errorf("提交事务: %w", err)`（不确定是否落库，日志要能分辨）。

**另外两条约定**

- **回调里只放数据库操作**：长耗时调用会占住唯一连接；`fn` 内 panic 时 `defer Rollback` 仍会执行，事务不泄漏。
- **`last_message_time` / `message_count` 的维护 SQL 与消息写入同一个回调**（§2 维护契约），不再有"repo 层是唯一入口"的约束——入口就是那段事务。

**新增 1 个 Go 依赖**：`github.com/openai/openai-go`（LLM 客户端，ADR-0014），已记入 `CLAUDE.md` 的「后端依赖补充」段；不引 Agent 框架。UUIDv7 用已有的 `github.com/google/uuid`；超时用 `context.WithTimeout`。ORM 仍是 sqlx，未换。

### 3.2 LLM 客户端：官方 `openai-go` + 全封装（ADR-0014，取代 ADR-0013）

**决策**：引 `github.com/openai/openai-go`，但**关在 `internal/llm` 一个包里**；对外仍是 `Stream` / `FetchModels` / `Summarize` 三个方法，`service` / `httpapi` 看不到任何 SDK 类型。

四条配套口径：

| 口径 | 值 |
|------|-----|
| 封装边界 | 全封装。SDK 只出现在 `internal/llm`；对外用自己的 `Message` / `StreamEvent` / `Usage`，包内做一次结构体互转（约 40 行） |
| 自动重试 | **关掉**（`option.WithMaxRetries(0)`）。SDK 默认对 429/5xx 重试 2 次，流式重试 = 重复计费 + 前端收到拼接回复。重试语义由我们定：**开流前**可重试一次；**写出 `start` 之后不重试**，只能走 `error` 事件 |
| `thinkingContent` | 从 SDK 响应对象的额外字段（`ExtraFields` / raw JSON）取 `reasoning_content`；流式 chunk 上取不到 → 退到「中间件截获原始响应体、第二遍解析」（约 30 行）；再不可用 → 字段恒为空（不改表、不改前端契约） |
| client 与超时 | **每次调用构造** `openai.Client`（`WithBaseURL` + `WithAPIKey`），不缓存；超时统一 `context.WithTimeout`（不用 `WithRequestTimeout`），与取消、NDJSON 写出对齐 |

**SDK 兜住的 vs 我们要兜的**（原来的"6 条边界"现在这样分）：

| 边界 | 谁负责 |
|------|--------|
| SSE 分帧 / 跨 chunk 半行 / CRLF / `[DONE]` / `bufio.Scanner` 64KB 行上限 | **SDK** |
| `context` 取消、超时中断读 body | **SDK**（我们负责把 ctx 传进去并在超时映射成 `调用超时`） |
| 流式 `tool_calls` 增量类型（`index` 归并 / `arguments` 分片） | **SDK 提供类型**；归并成"完整工具调用"是第二阶段 Agent 的事 |
| 非 200 的 JSON 错误体 → 可直出中文（`上游返回 401：api_key 无效`） | **我们**：`*openai.Error` → 中文 message |
| `reasoning_content`（DeepSeek 思考）、`usage` 归一 | **我们**（`usage` 从 SDK 类型取；`reasoning_content` 实测 `JSON.ExtraFields` **不填充**，改为对 `delta.RawJSON()` 二次解析——ADR-0014 预留的降级路径落地，粒度在单个 delta 上） |
| 自动重试次数 | **我们**（必须显式关掉，且要有一条"429 只请求一次"的测试） |
| `/v1/models` 拉取（#14 拉取模型列表、#15 检测连通复用） | **SDK**（`client.Models.List()`），我们只做错误映射与超时 |

**替换接缝**：换库只改 `internal/llm` 内部实现与结构体互转；`service` / `httpapi` / 测试（对着 `httptest` 假上游，`WithBaseURL` 指过去）都不受影响。

## 4. 非功能约束

- **鉴权/权限**：无。单用户本地工具，`127.0.0.1:1112` 监听（`config` 已固定）；不做 token、不做多租户。**不要**为此加中间件。
- **性能目标**：本地 SQLite，会话列表 20 行 < 50ms；消息列表 20 条 < 20ms；流式首字节取决于上游（不设目标），端到端硬上限 60s。
- **拉取模型列表（#14）**：`{baseUrl}/models` 上游耗时不可控，**超时 60s**（与聊天同口径，不单独配）；不落库、不缓存（每次点击都实拉，模型列表变动频繁，缓存反而误导）。
- **超时**：`-llm-timeout` 配置项，默认 60s（01-需求 约束）。实现为 `context.WithTimeout`，超时映射成 `error` 事件 `调用超时`。
- **并发**：
  - `MaxOpenConns=1` → 写串行，不会出现 SQLite 竞态。
  - 同一会话并发发送：进程内 `map[convID]struct{}` 互斥，第二个请求直接 **409 `该会话正在生成回复`**（前端已禁用输入，这是双保险）。
  - `seq` 由事务内 `MAX(seq)+1` 生成，`uk(conversation_id, seq)` 兜底冲突（冲突即 500 + 日志）。
- **幂等**：重试/编辑是"截断 + 重建"，同一 `messageId` 重复调用结果等价（消息 id 会重新生成）。删除会话幂等（404 之后重复删除返回 404，前端忽略）。
- **重试语义**（ADR-0014）：`openai-go` 的自动重试**已关掉**（`WithMaxRetries(0)`）。业务侧只允许**开流前**重试一次（用户无感，仍是 4xx/5xx 走 JSON）；**一旦写出 `start` 事件，绝不重试**，失败只能走 `error` 事件。理由：流式重试会让上游重复计费、前端收到两段拼接的回复。`Models.List`（#14/#15）不重试，失败直接 502 让用户点重试。
- **日志与可观测**：`slog` + chi `request_id`（已有）。**不记 `api_key`、不记消息正文**，只记 `conv_id`、`msg_id`、`content_len`、`model`、`duration_ms`、`upstream_status`。流式请求在 `start` 与 `done`/`error` 各打一条。**#14 只记 `service_provider`、`base_url` 的 host（不记完整 URL 查询串）、`model_count`、`duration_ms`、`upstream_status`**。
- **摘要**：assistant 消息落库后**异步**触发（`go` + 独立 context + 60s 超时，不继承请求 ctx），失败只记日志不影响响应；消息数 ≥ 10 且上次摘要 `message_seq` 小于当前最后一条时生成（01-需求 #4）。
  - **压缩范围**：截至最新 assistant 的**全部消息**（`seq <= last.Seq`）。与"最近 10 条"有重叠，属有意取舍——摘要是有损压缩，最近 10 条仍逐字发送，重叠不丢信息。
  - **写库**：`INSERT … ON CONFLICT(conversation_id) DO UPDATE`（upsert），锚点 `message_id` / `message_seq` = 最新 assistant。
  - **已知代价**：消息数超过 10 之后，每写一条 assistant 就会重算一次摘要（每次多一次上游调用）。MVP 按需求字面实现；将来可加"积压 N 条才重算"的阈值。

## 6. 实现顺序（给 `/flow-dev` 的建议，不是契约）

1. `internal/llm`（`Client.Stream` + `FetchModels` + `Summarizer`，用 `httptest` 假上游自测）→ 2. `service.ProviderService` + `httpapi/providers.go`（#10–#14：CRUD + 模型清单校验 + 拉取，无流式，先把错误映射跑通）→ 3. `service.ConversationService` + `httpapi/conversations.go`（#2–#5、#9，事务见 §3.1）→ 4. `service.MessageService` + `httpapi/messages.go` + `stream.go`（#6–#8，上下文组装、截断、摘要触发）→ 5. 前端联调。

顺序原则：先无流式的 CRUD（错误映射与事务样板一次定型），再上流式；每个 service 方法写完就能用临时真库独立 `go test`。

## 2. 规范与代码质量（次轴）

### 必须修（已修复 ✅）

- [x] **`internal/service/message.go:306-307`** — `assistantMessageId 与 userMessageId 不匹配` 校验无测试覆盖。**已修复**：补 `TestSendRegeneratePairingMismatch`（三子case：不存在 / 角色是 user / seq 在 user 之前，各走一条校验路径）；顺带把 `anchorMessage` 的 message 字符串匹配改成**哨兵错误 `errAnchorNotFound`**（建议改 1 一并解决），测试守护重映射。

### 建议改

- [x] **`internal/service/message.go:306`** — `anchorMessage` 的错误 message **字符串匹配**（**已随必须修一并改为哨兵错误 `errAnchorNotFound`**，测试守护）：`if ve, ok := err.(*ValidationError); ok && ve.Message == "userMessageId 指向的消息不存在或角色不支持"`。用 message 文本判断错误类型，`anchorMessage` 的文案一改，这里就静默不再重映射，用户会看到"userMessageId…"这个驴唇不对马嘴的错误（而实际是 assistantMessageId 的问题）。**建议**：让 `anchorMessage` 返回一个哨兵错误（如 `errAnchorNotFound = errors.New(...)`）或把错误文案作为参数传入，调用方按哨兵/文案映射，不依赖另一处的字面量。

- [ ] **`internal/service/message.go:148 + 356`** — `conversationTitle` 是一次**独立 SELECT**（每次发送都查一次会话标题）。而 `appendMessage` 刚刚在同一事务里 `UPDATE x_conversations SET title` 了。**建议**：让 `appendMessage` 返回标题（`appendedMessage` 加 `Title` 字段），省掉这次额外查询。每次发送省一个 round-trip；对高频操作（每条消息都发）有累积收益。非阻塞。

### 仅供参考

- `useChat.ts` 的 `retry`/`edit` 里 `if (!userMsg) return` / `if (!anchor) return` 是**静默返回**（用户点了没反应）。实际场景几乎不会触发（每个 assistant 都有前置 user），但若真触发，用户会困惑。可考虑留一行 `slog`/console 或 toast，但属于防御性边界，不强求。

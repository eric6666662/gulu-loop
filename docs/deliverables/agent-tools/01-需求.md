# 需求：agent-tools

> 交付物 01 · 由 /flow-grill 产出 · 设计/开发阶段以本文档为输入
> 依赖：`mvp-ai-chat`（已交付）—— 复用其会话/消息/流式/服务商全部能力

## 背景与动机

`mvp-ai-chat` 交付了"人和模型聊天"的完整链路。但聊天只能"说"，不能"做"：模型说"我帮你改这个文件"，实际改动得人自己动手。

第二阶段目标：让咕噜能**读、写、改本地代码并执行命令** —— 从"聊天工具"变成"能一起干活的 agent"。

**不做这件事的代价**：咕噜永远停在"问答助手"，每个需要落地的任务仍要在它和编辑器之间来回搬运。

**一个必须先兑现的旧承诺**：`mvp-ai-chat` 的 `01-需求` 写着"选型必须为第二阶段 Agent 让路：流式响应要能透传 `tool_calls` 增量"（ADR-0014）。但实测 `internal/llm.StreamEvent` 只有 `Delta` / `ThinkingDelta` / `Usage`，**`tool_calls` 从未透出**。"让路"只做到"选了 `openai-go`"，没做到"真的把工具调用信号交出来"。本需求第一件事就是补上这个管道。

## 目标

1. **补管道**：`internal/llm` 能透传并累积 `tool_calls` 流式增量。
2. **跑通循环**：`internal/agent` 实现手写的 ReAct 循环（模型要工具 → 执行 → 结果回填 → 继续），多步直到模型不再要工具。
3. **四个内置工具**：`read_file` / `write_file` / `edit_file` / `shell`。
4. **工作区约束**：每个会话绑定一个工作目录，文件类工具只能在工作区内操作。
5. **危险操作可控**：`shell` 首次调用需用户确认，确认后**本会话信任**，可随时关闭。
6. **全过程可见**：工具调用（工具名 / 参数 / 结果 / 状态）在消息区可见，并落库可回放、可导出。

## 非目标

- **MCP 协议**：将来考虑。本需求的工具接口要留接缝（工具实现同一 interface），但不做 MCP 客户端。
- **Skill（技能包 / 提示词模板）**：将来考虑。
- **多 agent 编排 / 子 agent**：不做。
- **Docker 化部署**：将来做（届时 `shell` 在容器内执行，装环境不影响宿主机）。**但本需求的路径设计必须按"容器内视角"表达**，使 Docker 化时挂载点不变、代码不改。
- **权限系统 / 多用户**：仍是单用户本地工具，无认证。
- **工具调用的细粒度审批**（每条命令单独白名单 / 命令解析沙箱）：本需求只做"本会话信任"这一档。
- **流式工具参数展示的逐字动画**：工具调用卡片一次性出现即可。

## 用户与场景

- 目标用户：单用户本地运行者（个人开发者），在本地跑咕噜、对着自己的项目目录说话。
- 典型场景 1：**改代码** —— "把 `internal/foo.go` 里的 `Bar` 函数改成用泛型" → agent 读文件 → 编辑 → 回报 diff 结果。
- 典型场景 2：**跑测试** —— "跑一下这个包的测试，失败的修掉" → agent 执行 `go test ./internal/foo` → 读失败输出 → 改代码 → 再跑（多步循环）。
- 典型场景 3：**新建文件** —— "给这个项目加一个 `Makefile`" → agent 在工作区内创建文件。
- 典型场景 4：**拒绝危险操作** —— agent 要执行 `rm -rf /`，用户点拒绝，模型收到"用户拒绝执行"，改为提出别的方案。

## 功能需求

| # | 功能点 | 描述 | 验收标准（可检验） |
|---|--------|------|--------------------|
| 1 | **`tool_calls` 管道** | `internal/llm.StreamEvent` 增加工具调用增量；`internal/llm` 内完成**增量累积拼接**（上游把一次调用切成多个 chunk，`arguments` 是分段字符串） | 1. 假上游返回 3 段 `tool_calls` 增量 → `Stream` 回调收到 3 次增量，累积后得到完整 `name` + `arguments` JSON；2. `arguments` 拼接后能被 `json.Unmarshal` 成功解析；3. 一次响应里多个并行 `tool_calls`（`index` 不同）能分别累积不串味；4. 无 `tool_calls` 时行为与现状完全一致（回归） |
| 2 | **agent 循环** | `internal/agent` 实现 ReAct 循环：调模型 → 有 `tool_calls` 就逐个执行 → 结果作为 `tool` 消息回填 → 再调模型 → 直到模型不再要工具或达到步数上限 | 1. 单轮工具调用：模型要 1 个工具 → 执行 → 回填 → 模型给出最终答复，共 2 次上游调用；2. 多轮：模型连续要工具 3 次 → 共 4 次上游调用；3. 达到**最大步数**（默认 20，可配）→ 停止并给用户明确提示，不静默截断；4. 循环中任一步上游失败 → 走 `error` 事件，已完成的工具调用结果保留在库 |
| 3 | **`read_file`** | 读工作区内的文本文件 | 1. 读工作区内文件 → 返回内容；2. 路径越出工作区（`../`、绝对路径）→ 拒绝并回填错误给模型，不执行；3. 文件不存在 → 回填"文件不存在"给模型；4. 大文件有大小上限（默认 1MB），超限回填错误 |
| 4 | **`write_file`** | 在工作区内创建 / 覆盖文件 | 1. 写入成功 → 返回"已写入 N 字节"；2. 父目录不存在 → 自动创建；3. 越界路径 → 拒绝；4. 覆盖已有文件时，工具结果里明确写"覆盖了已有文件"（让模型知道不是新建） |
| 5 | **`edit_file`** | 按精确文本替换修改文件（`old_string` → `new_string`） | 1. `old_string` 在文件中**唯一匹配** → 替换成功并返回替换处上下文；2. 匹配 0 次 → 回填"未找到匹配"（不写文件）；3. 匹配多次且未指定替换全部 → 回填"匹配到 N 处，请提供更精确的 old_string"（不写文件）；4. 越界路径 → 拒绝 |
| 6 | **`shell`** | 在工作区目录下执行命令，返回 stdout / stderr / exit code | 1. 执行成功 → 返回 stdout + exit code 0；2. 非零退出 → 返回 stderr + exit code，**不当作工具失败**（让模型自己判断）；3. 工作目录 = 会话工作区；4. 超时（默认 120s）→ 杀掉进程并回填"命令超时" |
| 7 | **每会话工作区** | `x_conversations` 增加工作区字段；会话创建时指定；文件类工具与 `shell` 的 cwd 都以它为准 | 1. 新建会话时指定工作目录 → 落库；2. 未指定工作区的会话，工具调用一律拒绝并回填"该会话没有设置工作目录"；3. 会话头显示当前工作区路径；4. 工作区不存在（被删/改名）→ 工具调用拒绝并回填明确原因 |
| 8 | **工作区边界** | 所有文件路径必须解析到工作区之内 | 1. `../../etc/passwd` → 拒绝；2. 绝对路径 `/etc/passwd` → 拒绝；3. **符号链接逃逸**（工作区内软链指向外部）→ 拒绝（用 `filepath.EvalSymlinks` 后校验）；4. 拒绝时把原因回填给模型，让它自己纠正 |
| 9 | **shell 确认（本会话信任）** | `shell` 首次调用需用户确认；确认后本会话内不再问；会话头可随时关闭信任 | 1. 本会话首次 `shell` → 前端出现确认（显示完整命令）→ 用户点"允许" → 执行；2. 点"拒绝" → 回填"用户拒绝执行该命令"给模型，循环继续（模型可换方案）；3. 允许后同会话后续 `shell` 不再确认；4. 会话头关闭信任后，下次 `shell` 重新确认；5. 信任状态落库（刷新页面仍生效） |
| 10 | **工具调用可见** | 消息区展示每次工具调用：工具名、参数、状态（执行中 / 成功 / 失败 / 被拒绝）、结果摘要 | 1. 工具调用出现时立即显示卡片（执行中态）；2. 完成后卡片更新为成功/失败并显示结果；3. 结果长文本默认折叠，可展开；4. 页面刷新后从库回放，卡片状态与内容一致 |
| 11 | **数据模型** | assistant 的 `tool_calls` 与 `tool` 结果落库，可回放、可导出 | 1. `x_messages` 能存 assistant 的工具调用（`tool_calls`）与 `tool` 结果（`tool_call_id`）；2. `GET …/messages` 返回这些字段；3. 导出 Markdown 包含工具调用（工具名 + 参数 + 结果摘要）；4. 上下文拼接时把 `tool_calls` / `tool` 结果按 OpenAI 协议正确回放给上游 |
| 12 | **中断** | 循环执行中用户可停止 | 1. 点「停止生成」→ 当前上游调用中止、正在跑的工具进程被杀；2. 已完成的工具调用结果保留；3. 状态回到可继续输入 |

## 约束

- 技术栈：沿用 `CLAUDE.md`（Go 1.26.1 + chi + sqlx + SQLite + `openai-go` v1.12.0 全封装；Vue 3 + TS + Tailwind v4）。
- **`internal/agent` 是新的顶层包**（与 `dal` / `llm` / `service` / `httpapi` 平级）。agent 循环是独立业务域，**不塞进 `MessageService`**。
- **`openai-go` 仍只在 `internal/llm` 出现**（ADR-0014 不破）。工具定义/调用类型由 `internal/llm` 用自有类型暴露，`agent` 不 import SDK。
- **工具接口化**：四个内置工具实现同一 interface（`Name` / `Description` / `Parameters`(JSON Schema) / `Execute`），为将来的 MCP 工具留接缝。
- **路径一律按「容器内视角」表达**：工作区路径就是容器内路径。将来 Docker 化时用挂载点对齐，代码不改。
- 工具执行**串行**（一次只跑一个工具），不做并行工具执行。
- 最大步数默认 20、`shell` 超时默认 120s、读文件上限默认 1MB —— 三个都可配。
- 沿用 `mvp-ai-chat` 的流式契约（ADR-0017 的 `meta`/`message`/`done`/`error`），**扩展**而非重写：新增工具调用相关事件/字段。

## 边界与异常

| 场景 | 预期行为 |
|------|---------|
| 会话未设置工作区 | 工具调用一律拒绝，回填"该会话没有设置工作目录"给模型 |
| 工作区路径不存在 | 工具调用拒绝，回填"工作目录不存在"；前端在会话头提示 |
| 路径越出工作区 / 符号链接逃逸 | 拒绝并回填原因（见 #8），**不执行任何 IO** |
| `shell` 用户拒绝 | 回填"用户拒绝执行该命令"，循环继续，模型可换方案 |
| `shell` 命令超时 | 杀进程，回填"命令超时（120s）"；不算循环失败 |
| `shell` 非零退出码 | 回填 stderr + exit code，**不算工具失败**（模型自己判断） |
| 工具参数不是合法 JSON | 不执行，回填"参数解析失败：<原因>"，模型可重试 |
| 工具名不在注册表 | 回填"未知工具：<name>"，模型可纠正 |
| 达到最大步数 | 停止循环，前端提示"已达最大步数（20），任务可能未完成"，已产生的消息与工具结果全部保留 |
| 循环中上游失败 | 走 `error` 事件；已完成的工具调用结果**保留在库**（可回放） |
| 用户中断 | 中止上游 + 杀工具进程；已完成结果保留 |
| 模型一次返回多个并行 `tool_calls` | **串行执行**（按 index 顺序），全部结果一起回填后再调模型 |
| `write_file` 覆盖已有文件 | 允许，但工具结果明确写"覆盖了已有文件" |
| `edit_file` 匹配多次 | 不写文件，回填"匹配到 N 处，请提供更精确的 old_string" |
| 同一会话并发发送 | 沿用现有 409「该会话正在生成回复」 |

## 开放问题

- [ ] **新建会话时工作目录怎么选？** 浏览器里拿不到本机绝对路径（`<input type="file" webkitdirectory>` 只给相对名，File System Access API 给的是 handle 不是路径）。三个选项：① 手填路径（最省事，MVP 建议）；② 后端加目录浏览接口 `GET /api/v1/fs?path=…`（能点选，但多一套 API + 安全面）；③ 启动参数给一个默认目录，会话创建时手填可覆盖。**建议 MVP 用 ①，目录浏览留到有反馈再加。**
- [ ] **工作区能否在会话创建后修改？** 建议允许（会话头可改），但改了之后历史工具调用记录里的路径仍指向旧工作区 —— 需要在 UI 上说明。
- [ ] **`edit_file` 是否支持 `replace_all`？** 建议支持（显式参数），否则批量改名类任务会很难受。
- [ ] **工具调用的 token 成本控制**：一次 `read_file` 可能是几千 token，多步循环很快撑满上下文。是否要在工具结果上做截断（如前 2000 行 / 前 50KB）？建议做，阈值待定。
- [ ] **`shell` 是否要限制为工作区内**？命令可以在任意路径操作（`cd /` 然后乱来）。本需求不做路径限制（shell 本来就是"逃逸口"，靠确认兜底），Docker 化后天然隔离。**这一点需要在设计阶段确认取舍。**

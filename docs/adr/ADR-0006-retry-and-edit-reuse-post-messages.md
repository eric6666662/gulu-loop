# ADR-0006: 重试 / 编辑后重发复用 POST messages，messageId 作为截断锚点

## 状态

已接受（2026-10-23）

## 背景

01-需求 要求两种操作：**重试**（对某条 assistant 回复重新生成）和**编辑后重发**（改自己的 user 消息后重新发起），两者的共同语义是"从某条消息开始，删掉它及其后所有消息，然后重新调 LLM 流式返回"。需求原文只说"请求体携带 messageId"，没定端点。

不决策的代价：前端 `useChat` 要写两套请求；后端要维护三条几乎相同的流式 handler；错误语义分叉。

## 决策

**不新增端点**。重试与编辑后重发都用 `POST /api/v1/conversations/{id}/messages`，靠 `messageId` 区分：

- `messageId` 指向 **assistant** → 截断该消息及其后，取**它之前最近的 user 消息**内容作为输入（= 重试）
- `messageId` 指向 **user** → 截断该消息及其后，取**请求体里的 `content`** 作为输入（= 编辑后重发）
- 不带 `messageId` → 追加新消息（普通发送）

## 权衡

| 备选 | 代价 | 为什么没选 |
|------|------|------------|
| 独立端点 `POST …/messages/{id}/retry`、`PUT …/messages/{id}` | 语义最直白 | 三条流式 handler 几乎逐行相同（上下文组装、NDJSON 写出、落库、超时、摘要触发），复制三份必然漂移；前端也要三套请求封装 |
| 用 `DELETE` + 再 `POST`（两次请求） | 复用现成接口 | 两次请求之间可插入别的写入，可能出现"删了但没重发"的中间态；前端要处理"删成功、发失败"的回滚 |
| 请求体加 `action: "retry" \| "edit"` 显式字段 | 可读性好 | 与 `messageId` 指向的角色重复表达同一件事（assistant=重试、user=编辑），两个字段可能互相矛盾，需要额外校验 |

## 后果

- **正面**：一条流式链路、一套错误语义、一份上下文组装逻辑；前端 `useChat` 只有一个 `send()`，`retry` / `edit` 只是不同的入参。
- **负面 / 代价**：`messageId` 的语义是**隐式**的（取决于目标消息的 `role`），必须在接口文档与代码注释里写死，否则新人会误以为"带 messageId 就是重试"。角色非法（system/tool）必须显式 400，不能静默当成追加。
- **后续跟进**：若将来出现"只重新生成某段而不删除后续"（分支对话）的需求，语义会冲突，届时需要独立端点并废弃本条。可逆性：中（前端只需改 `api/messages.send` 一个函数）。

# ADR-0004: 会话消息数用实时聚合，不加冗余列

## 状态

**已废弃（2026-10-23，被 ADR-0007 取代）** —— 用户决定改为在 `x_conversations` 上加 `message_count` 冗余列。本条保留作决策历史，实施以 ADR-0007 为准。

## 背景

UI 侧栏每一项要显示「N 条消息」（`02-ui设计.md` §3）。`x_conversations` 表没有这个字段，只有 `last_message_time`。两种做法：加冗余列并在每次写消息时维护，或在查询时聚合。

约束：SQLite 单文件、`MaxOpenConns=1` 串行写、单用户；消息量级是"个人使用，几千条"。列表每页 10–20 行。

不决策的代价：前端要么每个会话再发一次请求数消息（N+1），要么显示不出这个字段（UI 契约缺一块）。

## 决策

**查询时实时聚合**：`SELECT c.*, (SELECT COUNT(*) FROM x_messages m WHERE m.conversation_id = c.id) AS message_count`。**不新增列、不写迁移**。

## 权衡

| 备选 | 代价 | 为什么没选 |
|------|------|------------|
| `message_count` 冗余列 + 写时维护 | 列表查询最快 | 要在**四处**维护一致性：新增消息、重试截断（批量删）、删会话（级联）、删单条消息。任何一处漏掉就是长期脏数据，而且脏了没人发现。还要写迁移 + 回填存量 |
| 前端按需再查（N+1） | 零后端改动 | 20 行列表 = 20 次请求，本地也浪费；且每行都要 loading 态 |
| 只给 `lastMessageTime`、去掉消息数 | 最简单 | 违反 UI 契约（侧栏要显示「N 条消息」），要回 `flow-design-ui` 改设计 |

聚合的代价实测可忽略：子查询命中 `uk_x_messages_conversation_seq` 的索引前缀（`conversation_id` 打头），COUNT 是索引区间扫描；本地几千条消息、20 行的列表，总耗时 < 1ms 量级。

## 后果

- **正面**：零迁移、零一致性风险、零回填；`messageCount` 永远是真相（不会出现"显示 12 条实际 11 条"）。重试截断后计数自动正确。
- **负面 / 代价**：消息量涨到十万级、或未来要按消息数排序/筛选时，聚合会变慢，届时需要加列或加汇总表。
- **后续跟进**：监控点——单会话消息数 > 5000 或列表接口 p95 > 50ms 时，重新评估（加冗余列 + 事务内维护 + 一次性回填迁移）。可逆性：高（纯查询层改动，加列不影响现有数据）。

# ADR-0011: 服务商模型清单改为对象数组，能力字段只预留不实现，拉取模型列表只读不落库

## 状态

已接受（2026-10-23）· 修订 [ADR-0005](ADR-0005-provider-multi-model-and-apikey.md) 中 `models: []string` 的结论

## 背景

`01-需求.md` #1b / #1c 定稿后，服务商配置从"一个 `model` 字段 + 一堆模型名字符串"变成需要承载**模型元信息**：

- 用户要表达的不只是"这个服务商有哪些模型"，还有"这个模型能干什么"——能否读图、上下文多大，将来还有 token 计费。
- 但 MVP 的边界同时被钉死了：**只做聊天，不做图片识别**；摘要阈值固定 10 条，不按 token 预算。也就是说 `capabilities` / `context_window` / `pricing` 在 MVP 里**没有任何消费方**（没有发图入口、没有上下文预算计算、没有费用展示）。
- 存量 `setting_json.models` 是 `string[]`（ADR-0005）。字符串数组一旦有存量数据，**第一次加能力字段就得写一次"字符串 → 对象"的数据迁移**。

不决策的代价：要么现在把 6 个能力字段全做进表单（用户填一堆用不上的东西，后端校验全无消费方），要么继续用 `string[]` 并把将来的迁移债留给下一轮。

## 决策

**四件事一起定：**

1. **`models` 是对象数组** `[{id, name?}]`：`id` 必填（调上游时传给 `model` 字段），`name` 可选、缺省等于 `id`；至少 1 个元素；`id` 在服务商内唯一（忽略大小写）。
2. **默认模型强一致**：`model` 必须 ∈ `models[].id`，否则 400 `默认模型必须在模型清单中`。
3. **能力字段只预留键名，不实现**：`capabilities`（vision/tools/thinking/audio/json）、`context_window`、`max_output_tokens`、`pricing`、`deprecated`、`aliases`、`default_params`、顶层 `type`/`headers`/`proxy`/`timeout_ms`/`enabled`/`display_name` —— **不存、不显示、不校验**，键名写进 `02-后端设计.md` §2 锁定口径。
4. **拉取模型列表只读不落库**：`POST /api/v1/service-providers/models:fetch` 用 `{serviceProvider?, baseUrl, apiKey?}` 调上游 `GET /v1/models`，返回 `{models:["id",…]}`；写库仍然只由保存表单那一次 `POST/PUT` 决定。

存储仍是 `setting_json` TEXT（**snake_case**），接口仍是结构化 camelCase，转换只在 `ProviderSetting` 一处；读时兼容 `string[]` 与缺失 `models`（→ `[{id: model}]`），写时一律对象数组。

## 权衡

| 备选 | 代价 | 为什么没选 |
|------|------|------------|
| 继续 `models: []string` | 零改动 | 加能力字段时要写数据迁移（读旧字符串 → 写新对象），而且迁移必须在"上线再改"之外单独排期；现在改成本几乎为零 |
| 现在就把 `capabilities` / `context_window` / `pricing` 做进表单 | 字段一次到位，将来不用动 | **MVP 没有消费方**：不上传图片、不按 token 预算、不显示费用。做进去的唯一效果是表单变长、后端多 6 条没人验证的校验 |
| 独立表 `x_service_provider_models`（多模型可排序/可禁用/可 join） | 模型成为一等实体，将来按能力筛选、按价格排序都容易 | 为 4 张表的小工具加第 5 张表 + 联表 + 迁移；而"模型清单"天然是**服务商配置的一部分**（跟着服务商一起读、一起写、一起删），JSON 里存最贴合 |
| `GET /api/v1/service-providers/{name}/models`（按名字查） | 语义更 RESTful | 新建态（未保存）时服务商还不存在，拉不了 —— 而这正是最需要拉取的时刻 |
| `GET` + 查询串传 `apiKey` | 简单 | 密钥进访问日志 / 浏览器历史 / Referer；且"让服务端去调外部接口"不是幂等读，用 `POST` 更准确 |
| 拉取即覆盖 `models` 落库 | 用户少点一次 | "点一下按钮就把配置改了"是危险交互，且新建态没有记录可写；拉取=查询、保存=写入，职责分开 |
| 不提供拉取，纯手填 | 少一个接口 | 手填模型标识是这类工具最高频的踩坑点（`deepseek-v4-pro` 这种带版本号的），敲错要到运行时才报 400 |
| 上游失败细分 401/404/504 | 语义更精确 | 前端只有一条处理路径（提示 + 保留输入 + 引导手填），细分只会多写无用分支；原因放 `message` |

## 后果

- **正面**：将来加能力字段**不写数据迁移**（只需读写两侧同时上线，JSON 加键）；表单只放 MVP 真用得上的字段；拉取失败不会毁掉用户已填内容；默认模型与清单永远自洽，`ModelPicker` 初始值、发送消息缺省 `model` 都不必各自兜底。
- **负面 / 代价**：
  1. **破坏性契约变更**：`ServiceProvider.models` 从 `string[]` 变 `[{id,name}]`，前端 `api/providers`、`useProviders`、`ModelPicker`、服务商设置视图四处要改（已在 `02-后端设计.md` §5.1 逐条列出）。
  1b. **后续演进（2026-10-23）**：① 服务商设置从弹层改为右侧整屏视图，再改为「列表页 → 编辑页」两级（`02-ui设计.md` v10→v12）；② `models[]` 曾加过 `temperature` / `maxTokens` / `contextWindow` 三个参数（#1d），**随后按用户要求撤销**（v12）—— 加与删都只动了编解码与表单、表结构一动没动，这正是本 ADR "对象数组让加字段不写迁移"的两次实证；③ 新增 `website` 键（官网地址），同样零迁移。
  2. `PUT` 是全量覆盖：将来若某处写了未知键，保存一次就会被丢弃。MVP 没有写入方，属可接受；将来真要保留未知键，得把 `PUT` 改成"读-改-写"合并。
  3. 默认模型强一致把校验成本推给了表单（删掉默认模型那行时要自动改默认）。
  4. 拉取不缓存：每次点按钮都实拉上游，慢的时候用户要等（换来的是永远看到最新模型列表）。
- **可逆性**：高。能力字段随时可以加（JSON）；`models` 退回 `string[]` 也能靠"对象数组读时取 id"兼容。真正难逆的只有"前端已经按对象数组写"这件事。
- **验证方式**：`ProviderSetting` 编解码用表驱动单测覆盖四种存量形状（字符串数组 / 缺 `models` / 缺 `name` / 未知键）；校验用 8 条 400 用例；`FetchModels` 用 `httptest` 假上游覆盖 200 / 401 / 404 端点 / 非 JSON / 超时。

# ADR-0015: 服务商改为显式「激活」，模型引用带服务商身份

## 状态

已接受（2026-10-26）· 恢复并重定义 [ADR-0011](ADR-0011-provider-model-list-object-array.md) 中被撤销的 #1f「使用中的服务商」

## 背景

两个实测出来的 bug，同一个根因。

**Bug 1：切了模型，请求还是打到老服务商。** 两个服务商（`官方` / `中转站`）配置好后，前端在模型选择器里选「中转站 / gpt-4o」发一句，实测：

```
响应 start 事件: {"model":"gpt-4o","serviceProvider":"官方"}
上游日志:        [官方:18201] hit, auth=Bearer sk-官方, model=gpt-4o
```

根因在 `MessageService.Send`：

```go
provider, setting, err := ms.firstProvider(ctx)   // ORDER BY created_at LIMIT 1 —— 永远第一个
model := strings.TrimSpace(req.Model)             // 只当"发给上游的模型名"
```

`req.Model` **完全不参与选服务商**。也就是说：**"用哪个服务商"这件事从来没有被表达过**，它被隐式地钉死成"第一个"。

**Bug 2：中转站与官方有同名模型时无法区分。** 模型的唯一身份只有 `model` 一个字符串。`deepseek-chat` 在两个服务商下是同一个值，前端下拉里两行无法区分（选中态 `m.id === modelValue` 会让两行同时高亮），后端也无法区分。

**为什么会这样**：2026-10-23 撤销 #1f「使用中的服务商」时（UI 第三轮反馈：列表页不要「使用中」按钮），后端把"用哪个服务商"简化成"第一个服务商"。单服务商时看不出问题。

**关键判断**：#1f 被撤销掉的是**UI 按钮**，不是**这个状态本身**。"当前用哪个服务商"是必需的领域状态，删掉它并不会让它消失，只会让它变成隐式的 `ORDER BY created_at LIMIT 1`。隐式状态比显式状态更危险——用户改了配置却不知道生效的是哪一份。

不决策的代价：多服务商 / 中转站场景下**发错服务商**（错误的 base_url、错误的 api_key、错误的计费方），而且界面上看不出任何异常。

## 决策

**五件事一起定：**

1. **激活是全局唯一的，作用域是整个应用**（不是每个会话）。所有会话的后续消息都用这一个服务商的 base_url 与 api_key。
2. **允许「无激活」这个状态存在**（`0 或 1 个激活`），且**不会自愈**：
   - 从 0 个服务商变为 1 个（新增且表原为空）→ **自动激活**该服务商；
   - 删除激活的服务商 → 落到"无激活"，**不自动接替**；
   - 无激活状态下新增服务商 → **不自动激活**，由用户显式选择。
   - 无激活时：服务商页与聊天页两处横幅提示「请先激活一个服务商」，发送被禁止（400 `请先激活一个服务商`）。
3. **存储：`x_service_provider.is_active INTEGER NOT NULL DEFAULT 0` + 部分唯一索引** `CREATE UNIQUE INDEX … ON x_service_provider(is_active) WHERE is_active = 1`，在 DB 层强制"至多一个"。
4. **模型引用带服务商身份**：`POST …/messages` 请求体增加 `serviceProvider` 字段，与 `model` 一起标识"用哪个服务商的哪个模型"；`serviceProvider` **必须等于当前激活的服务商**（否则 400 `该服务商未激活`），`model` 必须在它的模型清单内（否则 400 `模型不在该服务商的模型清单中`）。
5. **前端模型选择器只列激活服务商的模型**；激活变化后当前模型若不在新清单内 → **回落到新服务商的默认模型**，并留下换模型痕迹（不允许静默）。

## 权衡

| 备选 | 代价 | 为什么没选 |
|------|------|------------|
| 保持现状（隐式"第一个服务商"） | 零改动 | 多服务商场景下**必然发错**，且界面无异常；实测已复现 |
| **每会话各自记服务商**（会话 A 用官方、B 用中转站） | 更贴近"会话独立"的直觉 | ① 与用户指定的入口（**服务商页面**激活）矛盾——那是全局的地方；② 多一个状态字段 + 一条派生规则（从最后一条 assistant 快照推）；③ 单用户本地工具，跨会话复用同一个服务商是常态，per-session 记忆是过度设计 |
| **复合字符串** `serviceProvider::model` 作为模型值 | 前端改动最小（值仍是 `string`） | **解析脆弱**：OpenRouter 的模型名本身就带 `/`（`anthropic/claude-3.5-sonnet`），任何分隔符都要处理转义；且这个值会进 JSON、日志、URL，处处要转义。两个独立字段是"类型即文档" |
| 只传 `model`，后端**反查**哪个服务商有它 | 请求体不变 | 同名模型**无解**（Bug 2 原样保留）；不同名时也得定优先级规则，等于把歧义从接口层藏到实现层 |
| 删除激活的服务商时**自动接替**下一个 | 永远发得出消息 | 删除会**静默改变后续消息的计费方**。用户明确选择了"不自动接替 + 提示去选"，即宁可卡一下也不要悄悄换 |
| 「无激活」不允许存在（永远恰好一个） | 状态机更简单（少一个空态） | 与"删除不自动接替"直接冲突；且用户明确要"没有激活的时候，提示用户自己去选择激活哪个" |
| 单行状态表 `x_app_state(key,value)` 存激活项 | 不污染服务商表 | 要处理"行不存在"的第三种状态，每次读激活服务商都要二次查询/JOIN；**服务商被删时还要写清理逻辑**。用列的话"行没了 → 激活自然消失"零代码 |
| 用 `updated_at` 最近的一条作为激活（不存列） | 零迁移 | 激活就变成了"谁最后被编辑"的副作用，编辑一个服务商的 base_url 会意外切走激活；且删除后无法表达"无激活" |
| `PUT {name}/active` + `{active:true/false}` | 更 RESTful、可逆 | 需求里**没有"取消激活"这个动作**（无激活只能由删除产生）。做成双向会诱导用户进入一个没有出口的状态（取消激活后必须再激活一个） |
| 激活时顺便校验连通性 | 早发现配错 | 网络抖动会拦住一次纯本地状态变更；连通性检测已是独立动作（#1g），不该捆绑 |
| 模型选择持久化到会话（刷新后还记得） | 更符合 #9 字面 | 本轮未定（已记入 `01-需求.md` 开放问题），按现状不持久化；若将来要加，是在本 ADR 之上叠加，不冲突 |

## 后果

- **正面**：
  - 「用哪个服务商」从隐式变成显式，**界面与实际请求永远一致**；Bug 1 与 Bug 2 同时消失（同名模型不再可能同时出现在下拉里）。
  - 部分唯一索引让"两个激活"在 DB 层就不可能，不依赖代码正确性。
  - 存量迁移回填"`created_at` 最早的一条"，**升级后行为与升级前完全一致**（旧代码就是 `firstProvider()`），不会因为这次改动突然换服务商。
  - `Delete` 不需要任何"接替"逻辑：行没了，`WHERE is_active = 1` 自然查不到。
- **负面 / 代价**：
  1. **破坏性契约变更**（4 处，已在 `02-后端设计.md` §5.2 逐条列出）：`ServiceProvider.isActive`、新增 `:activate` 接口、模型选择器数据源从"所有服务商"变成"激活的那一个"、`POST …/messages` 加 `serviceProvider`。
  2. **切换激活会静默改变已有会话的后续请求**（base_url / api_key / 计费方）。这是全局唯一激活的固有代价；缓解手段只有"换模型痕迹"与横幅，**没有**"会话级粘住"的保护。若将来发现这是真痛点，退路是叠加 per-session 覆盖（不改本 ADR 的数据结构）。
  3. **「无激活」是一个会卡住用户的状态**：删掉唯一的服务商后必须手动激活才能继续聊。这是刻意设计（宁可卡一下也不静默换计费方），但它确实是一个新的空态，前端两处横幅 + 禁用态都必须实现。
  4. **重试语义变了**：从"用原消息的模型"变成"用当前激活服务商 + 当前模型"（`01-需求` Q5 决策）。重试不再能复现当时的结果——这是为了让"激活决定一切"没有例外路径。若允许例外，就等于承认"非激活服务商也能被调用"，全局唯一激活的约束形同虚设。
  5. 模型选择仍**不持久化**（刷新回到激活服务商的默认模型），与 #9 "后续消息使用该 model 直到再次切换"的字面存在偏差，已记入开放问题。
- **可逆性**：中。
  - 加列 + 部分唯一索引容易回退（`Down` 迁移已写）。
  - 真正难逆的是**前端已按"模型值 = (serviceProvider, model) 二元组"写**，以及用户已经形成的"先激活再选模型"心智。退回隐式"第一个"会让 Bug 1 复现，实际不会退。
  - 若将来要支持 per-session 服务商：在 `x_conversations` 加可空覆盖列即可，本 ADR 的列与接口都不用改。
- **验证方式**：
  - 迁移：临时真库跑 `Up` → 断言存量多服务商时**恰好一条** `is_active = 1` 且是 `created_at` 最早那条；`Down` 后列消失。
  - 部分唯一索引：直接 `UPDATE` 两条为 1 → 断言唯一冲突。
  - `Activate`：404 / 成功 / 激活后再激活另一个 → 前者变 0。
  - 生命周期三条：空表新增 → 自动激活；删除激活者 → 无激活；无激活时新增 → 仍无激活。
  - `Send`：无激活 400；`serviceProvider` 不等于激活 400；服务商不存在 400；`model` 不在清单 400；正常路径断言假上游收到的是**激活服务商**的 base_url 与 api_key（这正是 Bug 1 的回归测试）。
